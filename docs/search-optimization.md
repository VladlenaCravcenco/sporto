# Поиск: переход на PostgreSQL

Сначала выполните **весь** `src/database/2026-09-28_search_rpc.sql` в Supabase SQL Editor. Он рассчитан на ранее установленный `2026-09-28_catalog_rpc.sql`.

После успешного выполнения на Mac, из папки проекта:

```sh
bash scripts/deploy-host.sh
```

Скрипт теперь проверяет обе новые функции с публичным ключом приложения **до переключения работающего сервиса**. Если SQL не установлен, публикация остановится, текущая версия продолжит работать. После переключения проверяется также `/api/search`; при ошибке восстанавливается предыдущий release.

## Что изменено

- Next.js больше не загружает весь каталог/описания/значения характеристик для поиска.
- Подсказки: один RPC, максимум 8 карточек без описаний. Полная выдача: максимум 24 карточки с корректным количеством и фильтрами, вычисленными в PostgreSQL.
- Код товара (`id`) использует имеющийся первичный ключ. Для нормализованного артикула (`sku`) добавляется B-tree индекс.
- Два частичных GIN-индекса для активных товаров: текст поиска и названия/бренд для опечаток. Это индексы выражений, новые столбцы в `SELECT *` не добавляются. Существующий `search_vector` не удаляется и не дублируется: его полнотекстовая семантика не заменяет поиск по подстроке/описанию и опечаткам.
- Правки товаров в админке автоматически обновляют индексы. Никакой отдельной синхронизации.
- Словарь RO/RU, синонимы, концепты и разбор цены остаются. Для опечаток вместо перебора расстояния Левенштейна в Node.js используется триграммное сходство PostgreSQL; отдельные результаты/порядок могут отличаться. Полное совпадение кода/артикула имеет приоритет и возвращает только совпадения кода.
- Кэш подсказок: максимум 32 коротких ответа, TTL 15 секунд, параллельные одинаковые запросы объединяются. Задержка ввода 250 мс и отмена старых запросов сохранены.
- RLS не меняется, функции SECURITY INVOKER. При отсутствии RPC нет скрытого отката на загрузку всех товаров.

Нулевого расхода RAM не бывает. Индексы занимают место в базе и требуют ресурсов при записи; цель — убрать большие снимки каталога из Node.js и обработку в браузере. Короткие или очень широкие запросы могут по-прежнему требовать сканирования в PostgreSQL. Реальный выигрыш измеряется после установки SQL, а не по факту успешной сборки.

## Проверка

Локально проверены адаптеры/ограничения/кэш и сборка. SQL не выполнялся на рабочей базе; миграция содержит вызовы обеих функций до COMMIT, так что ошибка прерывает транзакцию. Если редактор сообщает aborted transaction, выполните ROLLBACK перед повтором.

После публикации проверьте на сайте: код товара, RO/RU название, опечатку, синоним, запрос с ценой, отсутствие результатов, страницу 2 и сочетание поиска с фильтрами.

На сервере сравнивайте одинаковые запросы до/после и память после одинакового числа запросов:

```sh
systemctl show sporto -p MemoryCurrent -p MemoryPeak -p NRestarts
for i in 1 2 3 4 5; do
  curl -fsS -o /dev/null --max-time 30 \
    -w 'Search: %{time_starttransfer}s | %{size_download} bytes | HTTP %{http_code}\n' \
    'http://127.0.0.1:3000/api/search?q=insportline&lang=ro'
done
```

Это измеряет API, включая кэш. Для оценки самой БД в SQL Editor:

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT public.sporto_search_v1(
  '{"raw":["insportline"],"synonyms":[],"concepts":[]}', 'ro'
);
```

Внешний план функции покажет общее время/буферы, но не внутренние планы. Для проверки доступности триграммного индекса:

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT id FROM public.products
WHERE active=true AND public.sporto_search_document_v1(
  name_ro,name_ru,description_ro,description_ru,category,subcategory,brand,sku,id
) LIKE '%zenrun%';
```

На маленьком каталоге планировщик может обоснованно выбрать последовательное чтение. План/время в SQL Editor под владельцем не заменяют проверку RPC публичным ключом с RLS.

Основание для индексов: https://www.postgresql.org/docs/current/pgtrgm.html
